# vibe-coding: 같은 과제를 Codex에게 맡기면?

[sources/hayyoth/](../../sources/hayyoth/)에서 분석한 Hayyoth의 손코딩 과제를 **아무 맥락 없이** Codex에게 똑같이 맡겼습니다. 그리고 두 쪽의 접근 방식과 결과물을 비교했습니다.

## 1. 실험 설계

| 항목 | 내용 |
|---|---|
| 에이전트 | Codex CLI 0.160.0, 모델 `gpt-6.1-sol`, reasoning `high`, `codex exec` 비대화형 1회 실행 |
| 격리 | 과제마다 빈 작업 폴더(스크래치 경로)에서 실행. 이 리포와 sources/hayyoth 분석 내용은 프롬프트에도 작업 폴더에도 없음 |
| 프롬프트 | **영상 제목과 설명만** 옮겨 적음. 거기에 "C 컴파일러는 WSL에만 있으니 `wsl.exe -e cc ...`로 빌드하라"는 환경 안내 한 문단을 붙임 ([NN/PROMPT.md](02_tree/PROMPT.md)) |
| 권한 | Windows 샌드박스가 `wsl.exe`를 막아서 `--dangerously-bypass-approvals-and-sandbox`로 실행함. 사람처럼 직접 컴파일하고 실행할 수 있게 하기 위해서임(사용자 승인) |
| 기록 | `codex_events.jsonl`: 모든 명령과 편집 이벤트 / `codex_last_message.md`: 최종 보고 / `output/`: 작성한 파일 / `meta.txt`: 소요 시간 |
| 대상 | 02 tree, 03 움직이는 숫자, 05 파일 유틸, 07 연결 리스트, 08 동적 배열, 09 해시 테이블 |
| 제외 | 01(Hello World 선언문), 04(Lisp 강의), 06(기존 프레임워크 시연): 프로그래밍 과제가 아님 |
| 재현 | `bash run_codex.sh <과제> <빈 폴더>` / 비교: [compare/](compare/) |

과제별 프롬프트(환경 안내 문단 제외):

| # | 프롬프트 |
|---|---|
| 02 | Build your own tree directory viewer in C (a program like the Unix `tree` command). |
| 03 | Programming magical random moving numbers in C: write a C program that shows magical random moving numbers in the terminal. |
| 05 | Build Linux file utilities in C: touch, cat, mkdir, mv, rm and find. |
| 07 | Linked List data structure in C. Lisp makes it look easy, but in C, you have to build the whole world from scratch. |
| 08 | Dynamic Array in C: build a generic dynamic array from scratch in C using malloc and realloc. |
| 09 | Hash Table in C: build a hash table in C. |

## 4. 같은 과제, 다른 해석

가장 큰 차이는 코드 품질 이전에 **과제를 무엇으로 읽었느냐**입니다.

| 과제 | 사람이 만든 것 | Codex가 만든 것 |
|---|---|---|
| 02 tree | 재귀 원리만 담은 최소 구현. 정렬 없음, 숨김 파일도 출력, 들여쓰기와 색만 사용 | **진짜 `tree` 복제품.** 정렬, `├──` 가지선, 숨김 파일 필터(`-a`), 깊이 제한, 심볼릭 링크 대상 표시, 순환 감지, "N directories, M files" 요약 |
| 03 움직이는 숫자 | **규칙 시뮬레이션.** 입자 이동, 먹이, 보존 법칙을 바꿔 가며 "규칙이 행동을 만든다"를 보여 줌. 마지막 말은 "you write your rule" | **화면보호기.** 빛나는 숫자가 4가지 색 꼬리를 남기며 떨어짐. 30fps, 터미널 raw 모드, 창 크기 변경 대응, 키 조작(Space, +/-, R, Q) |
| 05 파일 유틸 | 명령마다 독립 파일. 직접 정한 CLI(`find PATTERN PATH`), `rm`은 기본이 재귀 삭제 | **POSIX 흉내.** `touch -acmhrt`, `cat -nbsvETA`, `mkdir -pvm`, `mv -finvT`, `rm -firdRv`, `find PATH -name GLOB`. 공통 라이브러리 `common.c`, `rm`은 `-r` 없이는 폴더를 거부, `mv`는 다른 장치 간 복사로 대체 |
| 07 연결 리스트 | **Lisp의 `map`/`apply`를 C로 옮김.** 함수 포인터로 고차 함수를 만들고 REPL과 나란히 비교 | **범용 리스트 라이브러리.** push/insert/pop/remove/find/reverse/clear, tail 포인터로 O(1) 추가. 프롬프트에 Lisp가 있었지만 **`map`/`apply`는 없음** |
| 08 동적 배열 | `len`/`cap`, 두 배 증가, `void *` + 원소 크기로 범용화. 핵심만 담음 | 같은 핵심 + `reserve`/`shrink`/`insert`/`erase`/`pop`, 오버플로 검사, **자기 원소를 다시 push할 때 `realloc` 별칭 문제**까지 처리 |
| 09 해시 테이블 | `SIZE 5` 고정, 글자 코드 합 해시, 체이닝. **이해하는 것이 목적**(ChatGPT 코드를 옆에 두고 다시 짬) | FNV-1a 해시, 부하율에 따른 확장, 키 복사, 값 갱신, 삭제, 내부 구조를 숨긴 타입 |

**요약**
- Codex는 모든 제목을 **"제품 사양"**으로 읽었습니다. 실제 도구와 똑같이, 견고하게, 기능을 더 많이.
- 사람은 제목을 **"보여 줄 개념"**으로 읽었습니다. 재귀, 규칙과 창발, Lisp와 C의 대비, 두 배 증가, 해싱과 충돌.
- 07번에서 차이가 가장 선명합니다. 영상 설명의 "Lisp makes it look easy"를 사람은 과제의 핵심으로 받았고, Codex는 사실상 무시했습니다.

양쪽 코드를 같은 gcc, ASan/UBSan, 같은 입력으로 실행했습니다([compare/behavior.sh](compare/behavior.sh), 결과 [compare/behavior_result.txt](compare/behavior_result.txt)).

| 08: 원소 1000개 | 정답 | 정답 |

## 6. 평가

### Codex 쪽

**장점**
- **견고함**: 같은 조건의 검사에서 결함이 0개였습니다. 메모리 해제, 오버플로, NULL, 별칭 문제까지 처리했습니다.
- **관례 준수**: 도구는 POSIX의 옵션과 오류 메시지 형식을, 라이브러리는 숨긴 내부 구조, `bool` 반환, 출력 인자로 결과를 돌려주는 계약을 따릅니다.
- **스스로 검증**: 테스트를 직접 쓰고 sanitizer로 돌려 통과시킨 뒤 보고합니다.
- **속도**: 과제당 2~9분입니다. 사람은 같은 과제에 15~52분을 썼습니다.

**단점과 특징**
- **범위가 넓어집니다.** 아무도 요청하지 않은 기능이 붙습니다(`cat -v`, tree 깊이 제한, 키 조작, 색). 코드는 4~9배가 되고, 개념을 보려면 helper와 계약 주석을 걸러 내야 합니다.
- **과제의 의도를 놓칩니다.** "Lisp makes it look easy"(07), "magical"(03) 같은 맥락을 기능 사양으로만 읽었습니다. 무엇을 보여 주려는 과제인지는 결과물에 드러나지 않습니다.
- **매번 같은 틀입니다.** 과제 크기와 상관없이 Makefile, README, `.gitignore`, 테스트, 헤더 분리가 나옵니다. 판단해서 나온 구조라기보다 기본값에 가깝습니다.
- **배우는 과정이 없습니다.** 한 번에 완성본을 쓰므로 왜 이렇게 생겼는지를 되짚을 단계가 남지 않습니다. 사람의 `history/`에 해당하는 것이 없습니다.

### 사람 쪽

**장점**
- **코드가 곧 개념입니다.** 43~72줄이라 한 화면에 들어오고, 모든 줄이 개념을 설명하는 데 쓰입니다(재귀 = 들여쓰기, `cap * 2`, `hash % SIZE`).
- **과제를 다시 정의합니다.** "숫자가 움직인다"를 "규칙이 행동을 만든다"로, "연결 리스트"를 "Lisp가 공짜로 주는 것을 C로 짓기"로 바꿔 읽었습니다.
- **과정이 남습니다.** 단계별 버전과 막혔던 지점(경고, segfault, AI 코드를 걷어 냄)이 그대로 학습 자료가 됩니다.

**단점과 특징**
- **엣지 케이스와 메모리 관리를 의도적으로 생략합니다.** 실사용 코드로 쓰려면 누수, UB, 크래시를 고쳐야 합니다.
- **관례와 다릅니다.** `rm`이 기본으로 재귀 삭제하는 것처럼 직접 정한 CLI는 위험한 기본값을 품기도 합니다.
- **테스트가 없습니다.** 확인은 화면에 보이는 시나리오에 한정됩니다.

### 결론

- 두 쪽은 같은 과제에서 **서로 다른 목적 함수**를 최적화했습니다.
  - Codex: "결과물이 완전하고 견고한가"
  - 사람: "만드는 사람(과 시청자)이 원리를 이해하는가"
- **사람의 09번 과정이 이 실험의 축소판입니다.** 사람은 ChatGPT가 준 완성형 해시 테이블(`SIZE 101`, djb2, `put`/`get`/`destroy`)을 옆에 두고, 그것을 이해하려고 가장 단순한 버전부터 다시 짰습니다. Codex의 결과물은 바로 그 "옆에 띄워 둔 완성본"에 해당합니다. 사람의 코드는 그 완성본을 이해해 가는 과정의 산물입니다.
- 따라서 둘은 경쟁 관계라기보다 **역할이 다릅니다**. 바로 쓸 부품이 필요하면 Codex 쪽이 낫고, 원리를 내 것으로 만들려면 사람의 방식(가장 단순한 버전부터 직접 치며 키우기)을 대신할 것이 없습니다.

### 실험의 한계

- 과제마다 Codex 실행은 한 번씩입니다. 같은 프롬프트로 다시 돌리면 결과가 달라질 수 있습니다.
- 프롬프트는 영상의 제목과 설명뿐이라, 시청자가 영상에서 얻는 맥락(REPL 시연, 배경 그림)은 Codex에게 주지 않았습니다. "최소한으로, 개념이 보이게"라고 지시했다면 결과가 달라졌을 것입니다.
- 사람의 코드는 영상에서 복원한 것입니다. 화면에 보이지 않는 공백 몇 바이트를 빼면 동작은 같습니다.
- 사람의 코드는 교육용 시연이고 제품을 목표로 하지 않았습니다. 견고함 비교는 사람 쪽에 불리한 기준입니다.

## 7. 재비교: 사람 코드의 남은 일을 같은 기조로 마무리했을 때

5절에서 드러난 결함과 저자가 TODO로 남긴 일을 **저자의 방식 그대로**(파일 하나, 최소 수정, 같은 스타일) 마무리했습니다. 결과는 [hand-completed/](hand-completed/)에 있습니다. 저자의 CLI, 기본 재귀 삭제, 고정 크기 해시처럼 설계로 볼 수 있는 부분은 손대지 않았습니다.

마무리하는 과정에서 처음 비교 때 놓친 **논리 버그 2개**를 더 찾았습니다.
- `touch`가 `fopen(path, "w")`라서 기존 파일 내용을 지움
- `mv`가 이미 있는 파일 위로 옮기지 못함. 저자의 설계 표("if target is file ..., rename")와 다른 동작

둘 다 메모리 오류가 아니라 의미가 틀린 경우라서 sanitizer로는 잡히지 않았습니다.

| | 사람 원본 | 사람 완결판 | Codex |
|---|---|---|---|
| 코드 줄 수 (6개 과제 합계) | 486 | **536 (+50, +10%)** | 2,524 (완결판의 4.7배) |
| 경고 (저자 플래그) | 0 | 0 | 0 |
| ASan/UBSan 검사 (07/08/09) | 누수, UB, segfault, 중복 키 | **모두 통과** | 모두 통과 |
| 05 유틸 시나리오 + 새 시나리오 4개 | 내용 삭제, mv 실패, find 오류, rm 누수 | **모두 기대대로** | 모두 기대대로 |
| tree, 파일 30만 개 | 1.3MB / 0.04초 | **1.4MB / 0.05초** | 62MB / 0.59초 |
| 연결 리스트 2만 번 추가 | 0.25초 | 0.23초(O(n) 유지) | **0.002초** |
| 바깥 의존성 | 없음 | 없음 | `-lm`, `common.c` 공유, `termios` |
| 테스트 | 없음 | 없음 | 6개 과제 모두 있음 |

### 이번 비교로 보이는 것

- **정확성의 격차는 50줄이었습니다.**
  - 원본과 Codex 사이의 2,000여 줄 차이 중 "올바르게 동작하게 만드는" 데 필요했던 것은 50줄(+10%)뿐입니다.
  - 나머지 약 2,000줄은 Codex가 정확성이 아니라 **다른 것**에 쓴 코드입니다: POSIX 옵션 호환, 정렬과 출력 꾸밈, 방어적 API 계약, 크기 확장, 테스트, 문서.
- **완결판은 4절의 장점을 그대로 지킵니다.** 수정 후에도 파일 하나, 한 화면, 스트리밍 출력(메모리 45배 적음), 의존성 없음입니다. `rm`은 마무리하면서 오히려 7줄 줄었습니다. 루프 안에서 파일과 폴더를 `walkrm` 하나로 처리하게 되면서 중복이 사라졌습니다.
- **Codex가 여전히 앞서는 것은 정확성이 아니라 설계 선택에서 갈리는 부분입니다.**
  - 표준 호환성: `find PATH -name`, `rm -r`
  - 규모 확장: tail 포인터, 해시 테이블 자동 확장
  - 안전한 기본값: `rm`이 폴더를 지우려면 `-r`이 필요함
  - **회귀 테스트**
- **테스트의 가치가 구체적으로 드러났습니다.** 이번에 새로 찾은 `touch`와 `mv` 버그는 "진짜 도구처럼 동작하는가"를 확인하는 테스트가 있어야 잡히는 종류입니다. Codex는 처음부터 그런 통합 테스트를 써서 같은 실수를 피했습니다. 사람 방식에 하나만 더 들인다면 가장 효과가 큰 것은 기능보다 **시나리오 테스트 몇 개**입니다.

### 수정한 평가

- 6절의 결론("서로 다른 목적 함수")은 그대로입니다. 다만 "사람 코드는 엣지 케이스를 생략한다"는 단점은 **약 10%의 코드로 메울 수 있는 격차**였습니다.
- 그렇게 메우면 사람 쪽은 **작고, 빠르고, 의존성 없고, 올바른** 코드가 됩니다. Codex 쪽은 **크지만 표준을 따르고, 확장 가능하고, 테스트로 보호되는** 코드입니다.
- 실사용에서 무엇을 고를지는 결국 4절의 질문으로 돌아갑니다. 알려진 맥락의 부품인가, 모르는 사용자를 위한 제품인가.

## 8. 리메이크: 사람 기조로 남은 약점까지 메웠을 때

완결판에서 남은 약점 중 쉬운 것을 사람 방식(파일 하나, POSIX 함수 활용, 같은 스타일)으로 메웠습니다. 결과는 [hand-remade/](hand-remade/)에 있습니다.
- 연결 리스트: append가 꼬리를 반환
- 해시 테이블: 크기 65536 + djb2 + 키 복사
- 유틸: `rm -r` 필수, `find` 글롭(`fnmatch`), `mkdir -p`
- `tree -s`: 정렬은 옵션으로만
- 셸 회귀 테스트 17개

| | 사람 리메이크 | Codex |
|---|---|---|
| 코드 / 테스트 | **605줄 / 44줄** | 2,524줄 / 913줄 |
| 경고, ASan/UBSan, 시나리오 | 모두 통과 | 모두 통과 |
| 연결 리스트 append 100만 | 0.030초 | 0.029초 |
| 해시 키 10만 (삽입+조회) | **0.008초** | 0.017초 |
| 해시 키 100만 (삽입 / 조회) | 0.22초 / 0.13초 | 0.21초 / **0.06초** |
| 동적 배열 push 1천만 | **0.040초** | 0.093초 |
| cat 200MB | **0.53초** | 1.79초 |
| tree 30만 개 (기본 / 정렬) | **0.05초·1.3MB / 0.13초·20MB** | 0.52초·62MB |

- 성능에서 Codex가 앞섰던 두 곳(연결 리스트, 해시 테이블)은 **각각 몇 줄로 동등하거나 앞서게 됐습니다.** 해시 조회만 100만 키에서 Codex가 2배 빠릅니다. 고정 크기라 체인이 평균 15까지 길어지기 때문입니다.
- 사람 쪽이 원래 앞서던 곳(tree, cat, 동적 배열)은 그대로입니다. `tree`는 정렬 옵션을 켜도 Codex보다 4배 빠르고 메모리는 ⅓입니다.
- 남은 격차는 GNU 옵션 호환, 방어적 API, 해시 자동 확장입니다. 모두 "범위"의 문제입니다.

### hand-remade를 "미니멀 코딩"이라고 불러도 되나?

**코드에 대해서는 대체로 그렇다. 하지만 이 채널이 말하는 미니멀 코딩이라고 부르기는 어렵다.**

**미니멀 코드로서 맞는 점**
- 크기가 문제에 비례합니다. Codex의 24% 크기로 같은 범위를 처리합니다.
- 프로그램마다 파일 하나이고, 공통 라이브러리, 숨긴 타입, 빌드 시스템이 없습니다.
- 필요한 일은 직접 짜지 않고 OS에 맡깁니다(`fnmatch`, `scandir`, `strdup`). "덜 쓰는 것"은 기능을 줄이는 게 아니라 이미 있는 것을 다시 만들지 않는 것입니다.
- 가정을 일반화하지 않고 드러냅니다. 해시 테이블은 "약 100만 키까지"라는 한계를 주석에 적고, 자동 확장을 넣지 않았습니다.

**걸리는 점**
- **기능이 필요가 아니라 비교에서 나왔습니다.** `tree -s`(22줄)와 `mkdir -p`(25줄)는 사용자가 요구해서가 아니라 Codex에 있어서 넣었습니다. 경쟁 상대의 기능 목록을 따라가는 것은 미니멀리즘의 반대 방향입니다(PHILOSOPHY D1, D3). 엄밀히 미니멀한 것은 완결판(536줄)이고, 리메이크는 "실사용 요구를 가정했을 때의 최소"입니다.
- **만든 방식이 다릅니다.** 이 채널의 미니멀 코딩은 결과물만이 아니라 과정입니다. AI 없이 손으로 치고, 가장 단순한 버전부터 컴파일하며 키우고, man 페이지를 읽습니다(PHILOSOPHY B1, C1, E1). hand-remade는 AI(이 분석을 한 에이전트)가 벤치마크를 보고 한 번에 고친 코드입니다. 스타일은 미니멀하지만 **손코딩은 아닙니다**.
- **이유의 출처가 다릅니다.** 저자의 코드는 그 개념을 이해한 결과라서 짧습니다. 리메이크는 측정 결과를 보고 고친 것이라, 같은 모양이어도 줄마다 담긴 이해의 깊이가 다릅니다. 09번 영상의 저자가 ChatGPT 코드를 옆에 두고도 직접 다시 짠 이유가 바로 이것입니다.

**정리하면**
- hand-completed: 미니멀 코드
- hand-remade: 실사용 요구를 받아들인 미니멀 스타일의 코드
- 이 채널의 의미에서 "미니멀 코딩": 이 리포에 있는 것 중에는 저자가 손으로 친 원본뿐입니다.
