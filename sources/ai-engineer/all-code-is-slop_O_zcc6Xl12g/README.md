## 1. 한 문장 요약

> 에이전트를 믿을 수 있게 만드는 것은 프롬프트가 아니라 **환경**이다. 에이전트를 고칠 때마다 그 교정을 규칙 문서 한 줄이 아니라 **기계가 강제하는 검사(린트, 타입, 테스트, 설계)**로 바꾸고, 생성보다 **검증**에 토큰을 더 써라. 그 기초 없이 자동화하면 슬롭만 늘어난다.

## 3. 포테이토 피라미드

```
          비용 낮음, 먼저 투자
 ┌──────────────────────────────────────────────┐
 │ codebase        좋은 API 설계, 아키텍처, 리팩토링   │  결정적: 코드 자체가 에이전트를 제약
 │ static analysis 린트, 타입, 컴파일러, 테스트, CI    │  결정적
 │ verification    형식(TLA+, Lean), 런타임           │  버그·불변식·의도 이해 확인
 │ prose           규칙, 스킬, AGENTS.md             │  판단이 필요한 것만
 │ human review                                     │  가장 비쌈
 └──────────────────────────────────────────────┘
          비용 높음
```
위 두 칸은 결정적이라서 "에이전트가 기본값으로 옳은 일을 하게" 만듭니다. 글(prose)은 맨 아래에서 두 번째입니다. **같은 교정을 AGENTS.md에 한 줄 더하는 것과 린트 규칙으로 만드는 것은 신뢰도가 다릅니다.**

## 5. pstack 저장소 대조 (2026-11-17 클론)

발표에서 이름이 나온 스킬은 모두 실제로 있습니다: `no-comments`(주석을 지우는 서브에이전트 "comment-sicko"를 부름), `create-verification-skill`(기능 지도와 앱 조종 스킬 생성), `create-formal-verification-skill`, `statechart`. 그밖에 원칙 스킬 24개(`principle-encode-lessons-in-structure`, `principle-fix-root-causes`, `principle-subtract-before-you-add`, `principle-attack-the-premise` 등)가 있습니다.

규모는 스킬 58개, 플레이북 22개, 문서 약 6,200줄, 스크립트·테스트 약 13,700줄입니다. "적게 쓰라"는 도구 자체는 작지 않습니다. 그 대부분은 검증 장치(상태도 생성기와 그 테스트 코퍼스)입니다.

## 6. 해석

- **핵심은 "글을 코드로 내린다"입니다.** 에이전트에게 같은 말을 두 번 하게 되면, 그 말을 규칙 문서에 적지 말고 린트·타입·폴더 경계·API 금지로 바꿉니다. 지켜졌는지를 기계가 확인하므로 사람이 기억할 필요가 없습니다.
- **주석을 바라보는 관점이 날카롭습니다.** 주석은 사람에게 쓰는 설명이기 전에, 에이전트가 "옳은 일을 안 한 이유"를 적어 두는 탈출구가 됩니다. 변명 주석이 붙은 땜질은 다음 에이전트에게 "허용된 패턴"으로 읽혀 복사됩니다(타이머 183개).
- **검증이 생성보다 중요해졌다는 것이 시대 판단입니다.** 예전에는 비싸서 못 쓰던 기법(형식 검증, 퍼징, 속성 기반 테스트)을 에이전트가 싸게 만들었습니다. 사람이 보는 대상은 코드가 아니라 증거(영상, 스크린샷, 상태도)로 바뀝니다.
- **순서가 처방입니다.** 코드베이스 → 정적 분석 → 검증 → 글 → 사람. 그리고 자동화(소프트웨어 공장)는 맨 마지막입니다. "나쁜 루프를 자동화하지 마라."
- **숫자는 자기 팀 홍보이기도 합니다.** 되돌림 비율은 품질의 대리 지표일 뿐이고, 성능 표의 퇴보는 말에서 빠졌고, Grok Bot과 pstack은 발표자 자신의 제품입니다. 원칙은 숫자가 없어도 성립하므로, 숫자보다 원칙을 가져오는 것이 맞습니다.

## 7. Hayyoth, 우리 northstar와의 관계

자세한 비교는 [sources/README.md](../../README.md)에 있습니다. 여기서는 요점만 적습니다.
- **같은 점**:
  - 둘 다 슬롭을 "AI 탓"이 아니라 환경과 습관의 문제로 봅니다.
  - Hayyoth가 경고를 최대로 켜는 것(C3)과 미묘한 언어 기능을 피하는 것(D2)은 피라미드 위 두 칸과 같습니다.
  - 진짜 도구와 출력을 나란히 비교하는 습관(A1)은 런타임 검증과 같습니다.
- **다른 점**:
  - Hayyoth는 사람이 모든 줄을 이해하는 것이 목적입니다.
  - poteto는 사람이 코드를 읽지 않아도 되는 상태("리뷰할 게 없다")가 목적이고, 사람은 증거를 봅니다.
- **우리 northstar에 주는 질문**: 리캐스트의 산출물 대부분(INTENT, TRACE, 파일 머리말 `Weak:`)은 피라미드의 **글(prose) 칸**입니다. poteto의 기준으로 보면 이것들은 강제할 수 없는 문서입니다. 회의론자가 찾은 결함을 린트와 검사로 내리는 단계가 우리 워크플로에는 없습니다.
