# Northstar: 의도 밀도 (Intent Density)

바이브 코딩으로 커진 프로젝트를 hand-remade의 기조로 되돌리기 위한 개념과 법칙입니다. 사람과 AI가 같은 기준으로 판단할 수 있도록, 모든 법칙을 **확인할 수 있는 형태**로 적었습니다. 근거는 이 리포의 실험([sources/hayyoth/](../sources/hayyoth/), [experiments/vibe-coding/](../experiments/vibe-coding/))입니다. 외부 출처([sources/](../sources/))에서 들여왔지만 아직 우리 실험으로 확인하지 않은 것은 *(가설)*로 표시합니다.

---

## 0. 한 문장

> **모든 코드는 코드 밖에 적힌 의도나 측정된 필요까지 거슬러 올라갈 수 있어야 하고, 그 조건을 만족하는 가장 작은 코드가 정답이다.**

이것을 최적화 문제로 쓰면 이렇습니다.

```
최소화   우연 코드 (의도로 거슬러 올라가지 못하는 코드)
조건     ① 의도 테스트가 모두 통과한다
         ② 측정된 자원 예산(시간, 메모리)을 지킨다
         ③ 신뢰 경계에서의 방어는 의도에 포함된다
허용     코드가 늘어나는 것은 ①~③ 중 하나를 새로 만족시킬 때뿐
```

`6+3`을 `(1×6−(1−1))+(1×3−(1−1))`로 쓰는 코드는 ①을 만족하지만 최소가 아닙니다. 반대로 `6+3`이 오버플로하는 환경이라 검사가 필요하다면, 그 검사는 ③에 해당하므로 우연이 아니라 의도입니다.

**최소는 줄 수가 계속 줄어든다는 뜻이 아닙니다.** 목표는 우연 코드가 0이 되는 것이고, 줄 수는 결과일 뿐입니다. [pilot-vnovel](pilot-vnovel/README.md)에서 다운로드 모듈은 556줄 → 371줄까지 줄었다가, 회의론자 라운드를 거치며 452줄로 늘었습니다. 늘어난 81줄은 모두 서버 오동작, 정체, 취소(③과 의도 D5~D7)를 가리킵니다. 371줄은 최소가 아니라 **모자랐던** 것입니다.

이 원칙을 기존 코드에 적용하는 절차가 **리캐스트**입니다([WORKFLOW.md](WORKFLOW.md)). 의도를 거푸집으로 삼아 코드를 다시 붓고, 동작은 보존하는 대신 의도에 맞게 다시 정합니다.

## 1. 의도 그래프

```
 의도 (INTENT.md)  ──검증──▶  행동 (의도 테스트)  ──구현──▶  코드 (TRACE.md로 연결)
      ▲                                                          │
      └───────────────── 근거 (LEDGER.md: 결정, 측정) ◀───────────┘
```

| 상태 | 의미 | 처리 |
|---|---|---|
| 의도 → 테스트 → 코드가 모두 이어짐 | 정상 | 유지 |
| 코드는 있는데 위로 이어지지 않음 | **우연 코드** | 삭제 후보. 이유를 찾으면 의도로 올림 |
| 의도는 있는데 테스트가 없음 | 보호받지 못하는 의도 | 테스트부터 작성 |
| 테스트는 있는데 의도가 없음 | 구현을 고정하는 테스트 | 의도로 올리거나 삭제 |

**의도 밀도** = (의도까지 이어지는 코드 줄) / (전체 코드 줄). 목표는 100%이고, 이 문서의 모든 법칙은 이 값을 올리는 방향입니다.

이 구조가 앞에서 제기한 문제("AI가 의도 밖 코드까지 다 이해해야 한다")를 직접 해결합니다. `TRACE.md`가 의도별 색인 역할을 하므로, AI는 수정하려는 의도에 연결된 파일만 읽으면 됩니다.

## 2. 개념

### C1. 본질 복잡도와 우연 복잡도
- 문제 자체가 요구하는 복잡도(본질)와 해법을 택하면서 생긴 복잡도(우연)를 구분합니다(Brooks, *No Silver Bullet*).
- **근거**: 사람 코드를 정확하게 만드는 데 든 것은 50줄(+10%)이었습니다. Codex와의 나머지 약 2,000줄 차이는 대부분 요구 없는 기능과 형식이었습니다.

### C2. 하지 않을 일(non-goals)은 할 일만큼 중요하다
- 범위를 정하지 않으면 생성 모델은 "이런 과제면 보통 이렇게 생겼다"는 평균으로 범위를 채웁니다.
- **근거**: 03번 "magical numbers"는 화면보호기가 되었고, 07번은 Lisp 맥락이 사라졌습니다.

### C3. 가정은 드러내고, 일반화는 측정이 요구할 때만
- "키 100만 개까지"처럼 한계를 이름 있는 상수와 주석으로 드러내는 것이, 쓰이지 않을 일반 장치를 넣는 것보다 낫습니다.
- **근거**: hand-remade의 `SIZE 65536`은 2줄이고, 키 10만 개에서 Codex보다 빨랐습니다.

### C4. 플랫폼이 먼저다
- OS와 표준 라이브러리가 이미 주는 것은 다시 만들지 않습니다.
- **근거**: `fnmatch` 한 줄로 글롭을 처리했습니다. Codex의 `find` 표현식 파서는 252줄입니다.

### C5. 데이터 표현이 설계다
- 자료 구조가 도메인 개념과 그대로 대응하면 코드가 줄고, 확장도 개념을 따라갑니다.
- **근거**: 03번은 `int` 하나로 빈칸/입자 수/먹이를 나타냈고, 이 코드가 06번 프레임워크로 자랐습니다.

### C6. 지역성: 한 단위는 혼자 읽혀야 한다
- 수정하려는 단위만 읽고 이해할 수 있어야 사람도 AI도 안전하게 고칩니다. 공유 모듈은 결합을 만듭니다.
- **근거**: Codex 05번의 `common.c`는 6개 도구가 공유해서, 하나를 고치면 6개가 영향을 받습니다.

### C7. 이해해서 고치면 코드가 줄어든다
- 원인을 이해한 수정은 중복을 없애므로 코드가 줄어드는 경우가 많습니다. 이해 없이 고치면 예외 처리가 하나씩 덧붙습니다.
- **근거**: `rm` 버그를 고쳤더니 63줄에서 56줄로 줄었습니다.

### C8. 테스트는 의도를 고정하는 장치다
- 테스트는 구현이 아니라 의도된 행동을 확인해야 합니다. 그래야 코드를 줄이는 리메이크를 안전하게 할 수 있습니다.
- **근거**: `touch`가 기존 파일 내용을 지우는 버그는 "진짜 도구처럼 동작하는가"를 확인하는 시나리오 테스트로만 잡힙니다. hand-remade는 44줄짜리 셸 테스트로 이를 고정했습니다.

### C9. 방어는 신뢰 경계에서
- 바깥에서 들어오는 입력(사용자, 네트워크, 공개 API 호출자)은 방어합니다. 내부 함수끼리는 서로 믿습니다.
- 이 구분이 Codex식 방어 코드와 사람식 신뢰 코드 사이의 긴장을 정리합니다. 경계에서의 방어는 의도이고, 내부의 중복 방어는 우연입니다.

### C10. 이해의 소유자가 있어야 한다
- 모든 줄을 설명할 수 있는 주체(사람이든, 문서와 함께 일하는 AI 세션이든)가 있어야 합니다.
- 설명할 수 없는 줄은 의도 그래프에서 끊어진 줄입니다.

### C11. 코드는 다음 작성자의 교과서다 — 교훈은 글이 아니라 기계 검사로 남긴다 *(가설)*
- 에이전트는 코드베이스에 있는 것을 "이 집의 방식"으로 복사합니다. 변명 주석이 붙은 땜질 하나가 패턴이 됩니다.
- 그래서 교정은 규칙 문서 한 줄(강제되지 않음)이 아니라 린트, 타입, 테스트, 폴더 간 import 금지, 위험한 API 제거로 남겨야 다시 생기지 않습니다. 새것을 먼저 막고 옛것은 그다음에 치웁니다.
- **근거**: 외부 출처 1개(poteto 발표: 타이머 땜질 1개 → 6주 뒤 183개, 주석 65,824 → 1,227, 교정 → 린트 계단 7 → 167, [sources/ai-engineer](../sources/ai-engineer/all-code-is-slop_O_zcc6Xl12g/)). Hayyoth의 경고 최대(C3)와 같은 방향입니다. 우리 파일럿에서는 아직 확인하지 않았습니다.

### C12. 대안과 겨뤄 보지 않은 코드는 "최소"라고 할 수 없다 *(가설)*
- 의도를 지키고 우연 코드가 없어도, 같은 의도를 더 작고 빠르게 이루는 기준 방법(기존 코드, 표준 라이브러리, 플랫폼, 잘 알려진 방법, 진짜 도구)이 있으면 그 코드는 최소가 아닙니다.
- 이 의심("왜 굳이?", "만들다 보니?")은 말로 답하지 않고, 기준 방법과 나란히 잰 결과로 답합니다.
- **근거**: Hayyoth는 진짜 도구를 명세이자 시험지로 씁니다(A1: `cal`과 나란히 비교). 회의론자 지적을 말로 기각했다가 틀린 경험도 있습니다([LESSONS](LESSONS.md) 5). 그러나 현재 회의론자 라운드는 "의도를 지켰나"만 묻고 "더 나은 방법이 있나"는 묻지 않습니다.

## 3. 법칙 (확인할 수 있는 규칙)

| # | 법칙 | 확인 방법 |
|---|---|---|
| L1 | **추적성**: 모든 파일과 공개 함수, 옵션은 `INTENT.md`의 항목이나 `LEDGER.md`의 측정 근거에 연결된다 | `TRACE.md`에 없는 파일은 gate가 실패시킴 |
| L2 | **성장 예산**: 줄을 늘리는 변경은 무엇을 새로 만족시키는지(의도, 측정, 경계 방어) 적는다. 줄을 지우는 변경은 근거가 필요 없다 | 변경 메모의 `Budget:` 항목 / gate의 순증가 검사 |
| L3 | **두 번째 실제 사용 전에는 추상화하지 않는다.** 추상화는 전체 줄 수를 줄일 때만 들인다 | 구현이 하나뿐인 인터페이스, 호출자가 하나인 래퍼 = 경고 |
| L4 | **의존성 최소**: 새 외부 의존성은 기록과 근거가 있어야 한다. 표준 라이브러리와 OS가 먼저 | 의존성 매니페스트 변경 시 gate가 근거를 요구 |
| L5 | **가정은 이름 있는 상수로**: 규모와 한계는 상수와 한 줄 주석으로 드러낸다 | 리뷰 항목 |
| L6 | **지워서 고치기 우선**: 버그 수정은 원인을 적고, 지울 수 있는지부터 검토한다. 특수 처리를 덧붙일 때는 "삭제로는 안 되는 이유"를 적는다 | 변경 메모의 `Root cause:`, `Deletion considered:` |
| L7 | **측정 후 성장**: 성능을 이유로 코드를 늘릴 때는 전후 벤치마크를 남긴다. 견고성을 이유로 늘릴 때는 먼저 실패하는 테스트나 sanitizer 결과를 남긴다 | `LEDGER.md`의 근거 링크 |
| L8 | **의도된 행동만 보존**: 리메이크 전에 의도된 행동을 특성 테스트로 고정한다. 의도가 아닌 행동은 명시적으로 버리고 `non-goals`에 적는다 | 의도 테스트 통과 + LEDGER의 Drop 기록 |
| L9 | **한 화면 단위**: 함수는 한 화면(약 40줄), 파일은 한 개념. 넘으면 이유를 적는다 | 정적 검사(경고 수준) |
| L10 | **오류 처리 방식은 하나**: 프로젝트 전체에서 한 가지 오류 전략을 쓴다 | 리뷰 항목 |
| L11 | **작고 검증된 걸음**: 모든 변경은 빌드, 테스트, sanitizer를 통과하는 작은 diff다 | CI |
| L12 | **경계에서만 방어**: 입력 검증은 신뢰 경계에. 내부 함수의 중복 방어는 삭제 후보 | 리뷰 항목 |
| L13 | *(가설)* **래칫**: 결함의 종류를 찾았거나 같은 교정을 두 번 했으면, 그 종류를 막는 기계 검사를 함께 넣는다. 땜질을 정당화하는 주석은 쓰지 않는다 | 변경 메모 `Ratchet:` / gate의 ratchet·excuse 경고 |
| L14 | *(가설)* **대안 대결**: 새 파일이나 예산을 넘는 성장은 기준 방법(기존 코드, 표준, 플랫폼, 잘 알려진 방법)과 크기·벤치마크를 나란히 잰 기록이 있어야 한다 | 변경 메모 `Alternatives:` / gate의 alternatives 경고 |
| L15 | *(가설)* **의심은 원장에, 답은 측정으로**: "왜 이렇게?"라는 의심은 `LEDGER.md`의 Doubts에 적고, 측정한 대결이나 소유자 결정으로만 닫는다 | Doubts 표: 열린 의심 수, 래칫으로 닫힌 비율 |
| L16 | *(가설)* **증거로 리뷰**: 의도마다 "무엇을 돌리면 무엇이 보이나"(`Proof`)를 두고, 변경은 그것을 실제로 돌린 결과를 첨부한다 | INTENT `Proof` 열 / 변경 메모 `Evidence:` |

L13~L16은 외부 출처 하나에서 들여와 아직 우리 파일럿으로 확인하지 않은 **가설**입니다. 파일럿에서 효과(줄어든 회귀, 막힌 재발, 찾아낸 더 나은 대안)를 확인하면 표시를 지웁니다. gate의 excuse 검사는 이 리포의 사람·AI 코드 111개 파일(16,730줄)에서 오탐이 0건이 되도록 낱말을 골랐습니다. 반대로 진짜 변명 주석을 찾은 실제 사례는 아직 없습니다(이 리포의 코드는 모두 한 번에 쓴 코드라 땜질이 쌓일 시간이 없었습니다).

## 4. 우연 코드의 냄새 (AI가 찾아야 할 것)

- 호출하는 곳이 없는 옵션, 플래그, 설정
- 구현이 하나뿐인 인터페이스, 한 번만 쓰이는 래퍼(`xmalloc`, `util_*`)
- 이름만 바꾼 중간 계층, 그대로 전달만 하는 함수
- `common`, `utils`, `helpers` 모듈: 호출자가 둘 미만이거나, 공유해서 오히려 줄 수가 늘어난 경우
- 내부 함수 안의, 불가능한 상태에 대한 방어
- 코드를 다시 말하는 주석, 계약 주석만 길고 쓰는 곳이 없는 API
- 스스로 확인하지 않는 테스트(구현 세부를 고정하는 스냅샷)
- 성능 근거 없이 넣은 캐시, 풀, 정렬, 버퍼링(근거: 02번 정렬 → 메모리 45배)
- 원인을 덮는 타이머, 재시도, sleep, 모든 예외 잡기, 그리고 그것을 정당화하는 주석(`// in case it comes back`, `// for now`, `// TODO`)
- 같은 모양의 땜질이 여러 곳에 복사된 것(하나는 사고, 여럿은 패턴)
- 규칙 문서(AGENTS.md, CLAUDE.md)에 적힌 금지 가운데 린트나 테스트로 강제할 수 있는데 글로만 남은 것
- 표준 라이브러리나 플랫폼이 이미 하는 일을 직접 구현한 코드(파서, 날짜 계산, 경로 순회)

## 5. 적용하지 말아야 할 곳

- **모르는 사용자를 위한 공개 라이브러리와 공개 CLI**: 방어적 계약과 표준 호환 자체가 의도입니다. 이 경우 Codex식 코드가 맞습니다(C9의 경계가 넓은 경우).
- **규제 환경**: 법적으로 요구되는 기록과 검증 코드는 의도입니다.
- **탐색용 프로토타입**: 버릴 코드라면 이 절차를 적용할 가치가 없습니다. 살아남기로 결정된 순간부터 적용합니다.
