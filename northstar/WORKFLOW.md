# 리캐스트(Recast) 워크플로

**리캐스트**는 의도를 거푸집으로 삼아 코드를 다시 붓는 일입니다. 바이브 코딩으로 커진 코드를 [NORTHSTAR.md](NORTHSTAR.md)의 의도 밀도 기조로 되돌립니다.

| | 동작 | 기존 코드 | 지키는 것 |
|---|---|---|---|
| 리팩토링 | **보존한다** | 구조만 바꾼다 | 기존 테스트 |
| 재작성 | 새로 정한다 | 버린다 | 새 테스트 |
| **리캐스트** | **의도에 맞게 다시 정한다.** 비목표는 지우고, 결함은 고치고, 의도의 공백은 소유자가 정한다 | 재료로 쓴다(코드, 커밋 이력, 실사용으로 쌓인 판단) | 먼저 만든 오라클(의도 테스트, 숨겨진 테스트, 벤치마크)과 회의론자 라운드 |

주조에 빗대면 이렇습니다. 거푸집(INTENT와 오라클)을 먼저 만들고, 원본을 부어 거푸집이 맞는지 확인하고, 녹여서(핵심을 다시 설계해서) 다시 붓고, 불순물(비목표와 장황함)을 걷어내고, 주물을 검사(회의론자)해서 기포(회귀)가 있으면 다시 붓습니다.

근거: [pilot-05](pilot-05/README.md) (합성 812줄), [pilot-vnovel](pilot-vnovel/README.md) (실제 앱의 모듈, main 병합), [LESSONS.md](LESSONS.md).

## 역할

| 역할 | 누가 | 하는 일 | 대신할 수 없는 이유 |
|---|---|---|---|
| **의도 소유자** | 사람 | `INTENT.md`와 비목표를 승인하고, Keep/Drop과 INTENT의 공백을 결정 | 무엇을 원하는지는 코드에 없음. 모델은 평균을 채움(NORTHSTAR C2) |
| **고고학자** | AI | 기존 코드, 문서, 커밋, 이슈, 사용 기록에서 의도 초안과 추적 지도를 만듦 | 읽는 양이 많은 일 |
| **오라클 제작자** | AI (빌더와 분리) | 의도 테스트, 숨겨진 테스트, 벤치마크, 테스트 서버·픽스처 | 빌더가 오라클을 보면 오라클에 맞춰 짬 |
| **빌더** | AI | 조각 단위 리캐스트와 자체 테스트 | |
| **회의론자** | 다른 모델, 읽기 전용 | 두 가지 일을 함: ① 회귀 리뷰(5단계): 원본과 결과를 INTENT에 대 보며 잃은 것과 새 결함을 찾음 ② 근본 회의(8단계): "왜 굳이 이렇게?"를 묻고 기준 방법과의 대결을 제안 | 같은 세션은 자기 결과를 확인 편향으로 봄 |
| **게이트** | 스크립트 + CI | [gate.py](gate.py), 테스트, sanitizer, 벤치마크 | 규칙을 사람의 기억에 맡기지 않음 |

## 단계

### 0단계. 동결, 기준선, 갈림길
- 현재 상태에 태그를 남기고, **실험은 별도 브랜치(worktree)에서** 합니다. main과 사용자 데이터는 건드리지 않습니다.
- 측정합니다: 줄 수, 의존성, 테스트와 커버리지, 벤치마크, 정적 분석.

#### 갈림길: 리메이크인가, 리캐스트인가 *(가설)*
둘은 같은 절차입니다. 다른 것은 **조각의 크기**뿐입니다. 리메이크는 "프로젝트 전체 = 조각 하나"로 놓고 1~6단계를 그대로 밟습니다. 그래서 의도(1단계)와 오라클(2단계)을 건너뛰는 리메이크는 없습니다.

| 이것이 참이면 | 고를 것 | 이유 |
|---|---|---|
| 틀린 전제가 뼈대(모듈 경계, 자료 형식, 전체 구조)에 깔려 있음. 같은 모양의 땜질이 여러 조각에 퍼져 있음 | 리메이크 | 조각 단위로 바꾸면 조각마다 같은 뼈대를 물려받음 |
| 철학(의도)이 바뀌어 공개 계약이 바뀌고, Drop이 기능의 절반을 넘음 | 리메이크 | 옛 계약으로 만든 오라클이 맞지 않고, 남길 재료가 적음 |
| 실사용으로 쌓인 판단이 적음(사용자 없음, 프로토타입) | 리메이크 | 리캐스트의 장점인 "원본을 재료로"가 약함 |
| 떼어 낼 경계가 없음 | 리메이크 | 옆에 새로 짤(strangler) 조각을 잘라낼 수 없음 |
| 전체가 한 조각 크기(대략 천 줄 이하) | 어느 쪽이든 같음 | 프로젝트가 곧 조각 |
| 크고, 실제로 쓰이고, 사용자 데이터나 다른 코드가 지금 계약에 기댐 | 리캐스트 | 한 번에 잃을 수 있는 것이 조각 하나뿐 |
| 개발을 멈출 수 없음 | 리캐스트 | 조각마다 병합하며 계속 배포 |

- 리메이크여도 **옛 프로젝트를 옆에 둡니다.** 2단계 오라클을 원본에 먼저 돌려, 실사용으로 쌓인 동작을 거푸집으로 떠 둡니다. 의도 없이 백지에서 짜면 슬롭이 반복됩니다(대조 실험의 Codex: 사람 코드의 7.6배, Brooks의 두 번째 시스템 효과).
- 근거의 한계: 모듈 규모에서만 확인했습니다. pilot-vnovel에서 의도만 보고 백지로 쓴 쪽(W2)은 빨라졌지만 혼합(W3)보다 덜 빨라졌습니다. 프로젝트 규모의 리메이크는 시험하지 않았습니다.
- **종료 조건**: 측정값이 `LEDGER.md`의 "Baseline"에 기록됨. 갈림길의 선택과 이유가 `LEDGER.md` Decisions에 한 줄로 있음(소유자 승인).

### 1단계. 의도 복원
- 고고학자가 초안을 만듭니다. 근거로 쓸 것: 문서, 커밋 메시지, 이슈, 사용 기록, 실제 호출부, 바이브 코딩의 프롬프트 기록(있으면 가장 강한 근거).
- 항목마다 출처를 붙이고, 출처가 없으면 "추정"으로 표시합니다. 공개 계약(다른 코드가 쓰는 시그니처)을 명시합니다.
- **소유자가 승인합니다.** 비목표와 규모 가정은 사람만 정합니다.
- **종료 조건**: `INTENT.md` 승인. 모든 항목에 ID가 있음.

### 2단계. 오라클 (가장 비싸고, 가장 중요)
리캐스트는 오라클의 구멍만큼 의도를 잃습니다. 빌더가 보는 테스트와 보지 못하는 테스트를 나눕니다.

1. **분류와 행동 고정**: 기능을 Keep / Merge / Drop / Unknown으로 나누고, Keep과 Unknown은 특성 테스트로 고정합니다.
2. **숨겨진 테스트**: 공개 계약만 쓰는 의도 테스트를 오라클 제작자가 따로 씁니다. 외부 의존(서버, 사이트)은 스크립트로 조종하는 가짜 서버나 녹화본으로 재현합니다. 정상 경로뿐 아니라 **오동작하는 상대**(끊김, 침묵, 거짓 크기, 범위 무시)를 흉내 냅니다.
3. **의도에서 뽑은 벤치마크**: 평균 상황뿐 아니라 의도가 걱정하는 상황을 넣습니다(예: 연결 일부만 느림). 표현 슬롭은 여기서 드러납니다.
4. **오라클 검증**: 원본에 먼저 돌려 녹색인지 확인합니다. 원본이 실패하면 원본의 결함인지 오라클의 결함인지 가립니다. **테스트가 INTENT보다 엄격하지 않은지** 확인합니다(pilot-vnovel에서 한 번 어겼습니다).
5. **변경 기록**: 오라클을 고칠 때마다 `ORACLE_CHANGES.md`에 남기고, 모든 버전에 다시 돌립니다.
- **종료 조건**: 원본이 오라클을 통과하거나, 실패한 항목이 "원본 결함"으로 확인됨.

### 3단계. 추적 지도와 슬롭 진단
- `TRACE.md`를 만들고 의도 밀도를 계산합니다.
- **슬롭의 종류를 가립니다.** 종류에 따라 도구가 다릅니다.

  | 종류 | 신호 | 도구 |
  |---|---|---|
  | 기능 슬롭: 아무도 원하지 않은 기능 | 의도 테스트가 실행하지 않는 코드가 많음 (pilot-05: 46%) | 비목표 목록으로 압축 |
  | 장황함 슬롭: 같은 일을 길게 함 | 커버리지는 높은데 코드가 길다 | 압축 (어떤 방법이든 비슷함) |
  | 표현 슬롭: 잘못된 자료 표현·알고리즘 | 의도에서 뽑은 벤치마크가 나쁨 (pilot-vnovel: 느린 연결 하나가 끝을 붙잡음) | 핵심 재설계 |

- **기준 방법과 겨뤄 봅니다** *(가설, L14)*. 핵심 조각마다 기존 코드, 표준 라이브러리, 플랫폼, 잘 알려진 방법, 진짜 도구로 같은 의도를 이룬 버전을 (가능하면) 만들거나 찾아서, 크기와 의도 벤치마크를 나란히 잽니다. 기준 방법이 크게 이기면 그 조각은 표현 슬롭입니다. 결과는 `LEDGER.md`의 Doubts에 적습니다.
- **종료 조건**: 조각마다 슬롭 종류와 고를 도구가 적혀 있음.

### 4단계. 조각별 리캐스트
조각 하나 = 의도 하나 또는 밀접한 의도 몇 개. **기본 전략은 혼합입니다.** 핵심(자료 표현, 스케줄링)은 의도에서 다시 설계하고, 주변부(입출력, 설정, 오류 처리)는 압축합니다. pilot-vnovel에서 혼합(W3)이 압축만 한 쪽(속도 그대로)과 백지 재작성(덜 빨라짐)을 모두 이겼습니다.

1. **목표 모양을 먼저 씁니다**: 자료 표현, 가정(이름 붙은 상수), 의도 ID. 파일 머리말 5줄(`Intent / Data / Assumes / Weak / Cost`)로 남깁니다.
2. **옆에 새로 짭니다**(strangler). 가장 단순한 버전부터 자체 테스트로 의도를 하나씩 고정합니다.
3. **주변부는 압축 루프로** 줄입니다(아래).
4. **오라클로 측정합니다**: 숨겨진 테스트, 벤치마크, 크기. 빌더에게 숨겨진 테스트는 보이지 않습니다.
5. **대조군**: 같은 원본을 오라클 없이 "최소화하라"고만 시킨 결과를 함께 잽니다. 효과가 절차에서 왔는지 구분하기 위해서입니다.

#### 압축 루프 (주변부와 기능·장황함 슬롭용)
라운드는 **모듈 → 함수 → 청크** 순서입니다. 매 라운드 단위마다 의도 ID를 적은 한 줄 머리 주석을 달고, INTENT와 비목표에 대 보고, 지우거나 머리 주석만 보고 다시 쓴 뒤, 검증하고 기록합니다. 의도 테스트가 실행하지 않는 줄이 다음 라운드의 지도입니다. 라운드 이득이 5% 미만이면 멈춥니다. 끝나면 *무엇*을 반복하는 주석은 지우고, 의도 ID와 *왜*만 남깁니다.

**압축은 지우기만 합니다.** 자료 표현이 문제라면 압축으로는 고쳐지지 않습니다.

### 5단계. 회의론자 라운드 (반복)
테스트 통과는 의도를 지켰다는 증거가 아닙니다. 고치는 일 자체도 새 회귀를 만듭니다.

1. **다른 모델이 읽기 전용으로** 원본, 결과, `INTENT.md`를 비교해 회귀와 결함을 찾습니다.
2. **지적을 분류합니다.**

   | 분류 | 처리 |
   |---|---|
   | 회귀 (이번에 생김) | 고침 |
   | 물려받음 (원본에도 있음) | 싸고 데이터 안전에 직결되면 고침, 아니면 기록 |
   | INTENT의 공백 | **소유자 결정**으로 올림 → 승인되면 INTENT 개정 |
   | 설계상 교환 | 머리말 `Weak:`와 INTENT에 공개 |

3. **말로 기각하지 않습니다.** 불가능함을 보이는 테스트로 기각하거나 소유자 결정으로 올립니다. pilot-vnovel에서 추론으로 넘긴 지적이 다음 라운드에 반례와 함께 돌아왔습니다.
4. **재현 테스트를 먼저 만들고, 고치기 전에 실패하는지 확인합니다.** 구현과 무관하게 쓸 수 있으면 숨겨진 테스트로(원본에도 돌림), 형식에 묶이면 자체 테스트로 만듭니다. 처음 만든 재현 테스트가 재현에 실패하는 일이 실제로 있었습니다.
5. **고친 뒤 돌연변이 검사를 합니다.** 고친 자리를 되돌리면 그 테스트가 다시 실패해야 합니다. 타이밍에 기대는 테스트는 여러 번 돌려 흔들림이 없는지 봅니다.
6. **다시 리뷰합니다.** 멈춤 기준: 직전 라운드에 심각도 높은 회귀가 없고, 남은 회귀는 테스트로 막았다. pilot-vnovel에서 새 회귀는 7 → 2 → 2 → 1건으로 줄었습니다.
- **종료 조건**: 멈춤 기준 충족. 처리표가 `ROUND.md`에 있음.

### 6단계. 통합과 실사용 확인
- 실험 브랜치에 넣고 **앱 전체** 테스트와 정적 분석을 돌립니다.
- 가짜 서버가 재현하지 못하는 것(TLS, HTTP/2, 실제 CDN의 습관)은 공개된 실제 대상에서 원본과 결과를 나란히 받아 비교합니다.
- **스모크 테스트 전에 관측성을 확보합니다.** 실패를 나중에 가를 수 있는 진단 로그(예: 창 생명주기)가 없으면 이상 현상의 원인을 영영 모릅니다.
- 데이터 형식이 바뀌면 **전환 메모**를 소유자에게 올립니다(마이그레이션 코드인가, 전환 절차인가).
- 프로젝트의 문서(예: ARCHITECTURE)를 같은 변경에서 동기화하고, 소유자 승인 뒤 병합합니다.

### 7단계. 정리
- 남은 우연 코드 정리: 구현이 하나뿐인 인터페이스, 한 번만 쓰이는 래퍼, 내부 중복 방어(L3, L12).
- Unknown으로 남은 기능을 다시 판단합니다.

### 8단계. 상시 회의 루프 *(가설: L13~L16)*
리캐스트는 누군가 마음먹어야 시작되는 행사입니다. 행사만으로는 "만들다 보니" 생긴 구조, 더 나은 방법이 있는데 굳이 고른 방식, 땜질로 쌓인 비효율이 다시 자랍니다. 그래서 리캐스트가 끝난 뒤에도 의심이 저절로 생기고, 측정으로 답해지고, 답이 기계 검사로 고정되는 루프를 계속 돌립니다.

**한 사이클 = 의심 → 대결 → 결정 → 고정**

| 단계 | 하는 일 | 남는 것 |
|---|---|---|
| 의심 | 아래 네 종류의 질문 가운데 하나를 구체적인 위치에 대해 적음 | `LEDGER.md` Doubts의 한 줄 |
| 대결 | 기준 방법과 지금 코드를 같은 오라클(의도 테스트, 의도 벤치마크)로 나란히 잼. 말로 답하지 않음 | 숫자 |
| 결정 | 지금 것 유지 / 그 조각만 리캐스트 / 소유자 결정(INTENT 개정) | Decision 열 |
| 고정 | 같은 종류가 다시 생기지 않게 하는 가장 싼 기계 검사를 넣음(린트, 타입, 테스트, import 금지, API 제거). 새것을 먼저 막고 옛것은 따로 치움 | Ratchet 열, 검사 코드 |

**네 종류의 의심** (회의론자의 근본 회의 질문)

| 종류 | 질문 | 대결 상대 |
|---|---|---|
| 전제 ("만들다 보니") | 이 요구를 처음부터 알았다면 이 구조로 지었을까? 같은 전제로 두 번 실패했다면 그 전제가 틀린 것 아닌가? | 요구를 처음부터 넣고 다시 설계한 핵심(혼합 리캐스트의 재도출) |
| 대안 ("왜 굳이") | 기존 코드, 표준 라이브러리, 플랫폼, 잘 알려진 방법, 진짜 도구로 하면 몇 줄이고 얼마나 빠른가? | 그 기준 방법으로 만든 최소 버전 |
| 땜질 | 이 분기, 타이머, 재시도, 방어, 주석이 덮고 있는 원인은? 같은 모양이 몇 곳에 있나? | 원인을 고친 버전(땜질을 지워도 의도 테스트가 통과하나) |
| 비용 ("왜 장황·비효율") | 의도 시나리오에서 시간, 메모리, 요청 수, 줄 수가 기준선이나 기준 방법보다 나쁜가? | 기준선 벤치마크와 기준 방법 |

**리듬** (누가 마음먹지 않아도 돌아가게)

| 언제 | 무엇 | 누가 |
|---|---|---|
| 모든 변경 | gate: `Ratchet:`, `Alternatives:`, 변명 주석 경고. CI: 의도 벤치마크와 크기를 기준선과 비교해 나빠지면 근거 요구 | gate.py, CI |
| 릴리스마다 | 다른 모델이 읽기 전용으로 근본 회의를 돌려 Doubts에 의심을 적음(가장 많이 바뀐 곳부터). 실제 앱을 사용자처럼 두드리는 탐색(퍼징)으로 증거를 모음 | 회의론자, 에이전트 |
| 정해진 주기(예: 한 달) | 열린 Doubts 가운데 하나 이상을 대결로 닫음. 지울 것을 하나 이상 찾음(덜어내기). 글로만 남은 규칙(AGENTS.md, `Weak:`)을 검사로 내릴 수 있는지 봄 | 빌더, 소유자 |
| 새 기능 | INTENT 항목(`Proof` 포함) → 테스트 → 기준 방법과 대결 → 코드 | 빌더 |

멈추면 안 되는 이유: 회의론자 라운드에서 배웠듯이 고치는 일 자체가 새 회귀를 만들고([LESSONS](LESSONS.md) 4), 코드베이스에 남은 땜질은 다음 작성자가 복사합니다(NORTHSTAR C11).

## 모든 변경에 거는 게이트

| 검사 | 기준 | 실패 시 |
|---|---|---|
| 추적 | 바뀐 소스 파일이 모두 `TRACE.md`에 있음 | 실패 |
| 성장 예산 | 순증가가 예산을 넘으면 변경 메모에 `Budget:` 근거 | 실패 |
| 새 파일 | 새 파일은 `TRACE.md`에 의도와 함께 추가 | 실패 |
| 의존성 | 매니페스트가 바뀌면 `LEDGER` 근거 | 실패 |
| 수정의 원인 | 버그 수정이면 `Root cause:`, `Deletion considered:` | 경고 |
| 돌연변이 검사 | 버그 수정이면 `Mutation:` (되돌리면 실패하는 테스트 이름) | 경고 |
| 테스트 | 의도 테스트, 숨겨진 테스트, 특성 테스트, sanitizer, 정적 분석 통과 | 실패 |
| 성능 | 성능 경로를 바꾸면 벤치마크 전후 비교 | 경고 |
| 래칫 *(가설)* | 버그 수정이면 `Ratchet:` (그 종류를 막는 검사, 없으면 `none: 이유`) | 경고 |
| 대안 *(가설)* | 새 소스 파일이나 예산 초과면 `Alternatives:` (기준 방법과 잰 결과) | 경고 |
| 변명 주석 *(가설)* | 새로 더한 주석에 땜질을 정당화하거나 미루는 말(workaround, in case, for now, TODO 등)이 없음 | 경고 |

[gate.py](gate.py)는 테스트와 성능을 뺀 나머지를 git diff와 변경 메모에서 확인합니다. 테스트와 성능은 CI에서 돌립니다.
