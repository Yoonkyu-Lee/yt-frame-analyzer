# W2 ROUND: 의도에서 다시 도출한 segmented_download

## 1. 설계 (코드 전에)
**데이터**
- 파일 = 1 MiB 조각(`CHUNK`)의 배열. 조각 i = 바이트 `[i*CHUNK, min((i+1)*CHUNK,total)-1]`.
- 스케줄: 아직 못 받은 조각 번호 `pending: Vec<u64>` + 공유 `AtomicUsize next`. 일꾼(최대 8개, D3)이 `next`를 하나씩 올려 가며 가져간다(작업 큐). 정적 분할을 쓰지 않는 이유: uneven에서 느린 연결에 걸린 일꾼이 큰 몫을 쥐면 끝까지 기다린다. 작은 조각 큐면 느린 연결의 피해가 조각 하나로 한정된다.
- 이어받기 상태: `<dest>.part`(총크기로 미리 늘린 본문) + `<dest>.map`(`[총크기 u64 LE][조각당 1바이트 0/1]`). 조각은 메모리에 통째로 받아 검증한 뒤 `.part`에 쓰고 flush, 그 다음에야 `.map`의 해당 바이트를 1로 쓴다. 따라서 map이 1이면 본문은 이미 디스크에 있다.
- 완료 감지: 모든 일꾼이 큐를 비우고 오류/취소가 없으면 완료. `.part`를 `dest`로 rename(D1: 완성 후에만 나타남), `.map` 삭제.
- 시작 시 상태 검증: map 길이 = 8+조각수, 헤더 총크기 일치, 값이 0/1, part 길이 = total. 하나라도 틀리면 버리고 새로 시작(D4 다른 크기, D5 손상).
- Single 경로: `.part`에 스트림, 끝나면 rename. 실패/취소 시 `.part` 삭제(이어받기 비목표). 탐색 요청이 200이면 그 응답을 그대로 본문으로 쓴다.

**상수와 가정**
| 상수 | 값 | 가정 / 의도 |
|---|---|---|
| CONNECTIONS | 8 | D3 상한 |
| CHUNK | 1 MiB | D4(재다운로드 <= ~1 MiB/연결), P1(느린 연결의 피해 상한). 더 작게 해도 uneven 하한은 같음(아래 3절) |
| TRIES / BACKOFF | 4 / n*200ms | D6: 영구 실패는 총 1.2초 대기 후 Err |
| REPORT_EVERY | 250ms | D8 |
| CONNECT_TIMEOUT | 20s | D9 |
| STALL_TIMEOUT | 30s | 읽기가 멈춘 연결 방지(의도 밖 안전장치, 정상 흐름에는 영향 없음) |

**검증(D5)**: 조각 응답은 206 + `Content-Range == bytes a-b/total`(요청한 구간, 같은 총크기)이어야 하고, 받은 길이가 정확히 `b-a+1`이어야 한다. 아니면 그 조각만 재시도, 4번 실패하면 Err. 검증 전에는 파일에 쓰지 않는다.

## 2. 진행 단계
1. 단일 스트림 + 공개 계약(토큰 맵, 구조체) 먼저. 컴파일 확인.
2. 탐색 요청 + 206/200/`*` 분기, Range 조각 + 일꾼 풀 + part/map. 컴파일은 한 번에 통과.
3. 벤치: `throttled 1.12s | uneven 4.35s | unthrottled 0.49s` (기준 1.09 / 6.08 / 0.50).
4. 테스트 14개(D1~D10, std TcpListener 서버 내장). 첫 실행 3건 실패 후 원인 분석:
   - **D9 실제 버그**: reqwest가 리다이렉트 때 자동 Referer로 우리 Referer를 덮어씀 -> `.referer(false)`로 수정.
   - 테스트 서버가 마지막 조각 후에도 sleep해서 동시 접속이 9로 보임 -> 서버를 실제 `src/server.rs`처럼 마지막 sleep 생략.
   - 이어받기 테스트 타이밍(취소 시점에 완료된 조각이 없었음) -> 지연 20ms, 취소 450ms.
5. 최종: 14/14 통과(4회 연속 반복), 벤치 `throttled 1.14s | uneven 4.34s | unthrottled 0.58s`(0.49~0.58 편차). 코드 349줄(규칙대로 센 값, 테스트 제외).

## 3. 결정 (의도 ID)
- 큐 + 작은 조각 (D3, P1): uneven은 "3번째 연결마다 1 MB/s"이고 이 서버는 요청마다 새 연결이라 느린 연결 몫이 전체 바이트의 1/3이다. 느린 쪽에서 27 MB가 1 MB/s로 흐르므로 8연결 하한은 약 (27+5.3)/8 = 4.0초. 측정 4.34초는 이 하한에 가깝다. 이보다 줄이려면 느린 연결을 도중에 끊고 재요청해야 하는데(복잡도 증가) 하지 않았다. 의도(P1: 퇴보 금지)는 충족.
- 조각을 메모리에 모아 검증 후 쓰기 (D5): 틀린 구간/길이가 파일에 닿지 않는다. 대가는 일꾼당 1 MiB 메모리.
- map을 본문 flush 뒤에 갱신 (D4): 앱이 어느 시점에 죽어도 map=1이면 본문 존재.
- 상태는 URL이 아니라 대상 경로 + 총크기로만 식별 (D4): 서명 URL은 매번 바뀌므로 URL을 키로 쓰면 이어받기가 불가능. 대신 같은 크기의 다른 파일이면 섞임(Weak에 명시).
- 탐색 응답 416/206(총크기 불명)은 Range 없는 GET으로 Single (D2). 0바이트 파일은 서버가 200을 주므로 Single로 빈 파일 생성.
- 진행률은 재시도 때 되돌리지 않고 `max(마지막 보고값)`으로 보고, 마지막 이벤트는 `finish`가 total로 강제 (D8).

## 4. 열린 의문
- Single 경로에서 총크기를 모르면 마지막 이벤트의 `total`을 받은 바이트로 채움(Some). "모를 때 None 유지"를 기대하는 테스트가 있으면 어긋날 수 있음.
- 취소가 거의 끝난 시점에 걸리면 완료된 파일이 있어도 `Ok(None)`을 돌려줄 수 있음(상태는 보존되어 다음 호출이 즉시 끝남).
- 느린 연결 중도 포기(hedging)는 구현하지 않음. 큰 파일에서 1 MB/s 연결이 조각당 1초 걸리는 정도의 꼬리는 허용.
- 디스크 쓰기는 조각마다 파일을 다시 열어 쓴다(단순함 우선). 512MB 벤치에서는 문제 없었음.
- 긴 정지(30초 STALL_TIMEOUT) 후 재시도 시 최악 시간은 4*30초: "영구 실패는 수 초" 요구는 연결 거부/오류 응답에 대해서만 보장됨.
