# pilot-vnovel: 실제 바이브 코딩 프로젝트에서의 워크플로 대결

**대상**: VNovel Library(Rust + Tauri, 약 3만 줄)의 `src-tauri/src/segmented_download.rs`. 배포처에서 얻은 최종 URL을 Range 분할(최대 8연결)로 받고, 재개·재시도·취소·진행률을 맡는 모듈입니다. 원본은 890줄이고 테스트를 뺀 코드는 556줄입니다. 실사용으로 검증된 코드입니다(4.22GiB 파일의 SHA-256 일치).

**질문**: 같은 모듈을 네 가지 방식으로 다시 쓰면 무엇이 달라지는가? 크기, 숨겨진 의도 테스트, 성능, 읽기만으로 예측할 수 있는 정도(정적 투명성), 그리고 회의론자가 찾는 새 결함 수를 비교합니다.

원본 저장소의 main은 건드리지 않았습니다. 실험 브랜치 `exp/northstar-segmented`를 별도 worktree(`../vnovel-library-exp`)로 열고, 최종 후보 W4만 그 브랜치에 커밋했습니다(`6eff24b`, `2635a26`, 푸시하지 않음). 라이브러리 데이터는 `F:\VNovel`에서 가장 작은 항목 `v26537` 하나만 [library/](library/)로 복사해 썼습니다.

## 무엇을 배웠나

1. **이 모듈의 슬롭은 "기능"이 아니라 "말투"였습니다.** 비목표 기능이 거의 없었기 때문에, 의도 문서 없이 최소화만 시킨 대조군도 33%를 줄였습니다. pilot-05에서는 대조군이 7%밖에 줄이지 못했습니다. 그때 압축 루프가 이긴 이유는 비목표 목록이었는데, 여기서는 그 목록이 거의 비어 있었습니다. 줄어든 것은 sidecar 3개를 1개로 합친 것, 문자열 sentinel, 진행률 구조체, 인자 9개짜리 함수 같은 장황함입니다. 네 방식 모두 그 정도는 비슷하게 걷어냈습니다.
2. **"발상의 전환"은 재설계한 쪽에서만 나왔습니다.** 원본의 16구간 동적 분배는 느린 연결의 꼬리를 막지 못했습니다(6.09초). 알고리즘을 바꾸지 말라고 한 W1과 대조군은 그대로였습니다. W2는 1MiB 조각 큐로 4.35초, W3는 "남은 구간 목록 + 빈 연결이 가장 많이 남은 연결의 뒷절반을 넘겨받기"로 **2.32초(2.6배)**까지 줄였고, 제한 없는 경우에도 가장 빨랐습니다. pilot-05에서 세운 가설 "압축은 지우기만 할 뿐 자료 표현을 바꾸지 못한다"가 여기서 측정으로 확인됐습니다.
3. **많이 바꿀수록 회의론자가 찾는 새 결함이 늘었습니다.** 숨겨진 테스트 23개는 모두 통과했는데도, 회의론자는 구조를 많이 바꾼 W1·W2·W3에서 각각 7~8건, 구조를 거의 유지한 대조군에서 3건을 지적했습니다. 대부분 재개 상태의 크래시 내구성, 취소 경계, 탐색 응답 처리 같은 드문 경로입니다. pilot-05의 교훈(압축은 오라클의 구멍만큼 의도를 잃는다)이 재설계에서도 똑같이 성립합니다.
4. **반대로 의도를 가진 쪽만 원본의 버그를 찾았습니다.** W1·W2·W3는 각자 D9를 테스트로 고정하다가, reqwest가 리다이렉트할 때 호출자의 Referer를 덮어쓰는 원본 버그를 발견해 고쳤습니다. 대조군과 제 숨겨진 테스트는 이 버그를 놓쳤습니다.
5. **정적 투명성 측정기는 천장에 닿았습니다.** 원본부터 12/12였습니다. 이 정도 크기의 모듈에서는 AI 독자가 거의 모든 행동을 맞힙니다. 측정기가 잡아낸 차이는 둘뿐입니다.
   - W3의 넘겨받기는 타이밍에 따라 요청 수가 달라져(20~25회) 읽기만으로는 예측할 수 없습니다. 성능과 예측 가능성 사이의 실제 교환입니다.
   - 머리말의 `Weak:` 줄이 실제 약점("같은 크기의 다른 파일이면 섞임")을 정직하게 드러냈고, 실행 결과와 일치했습니다.

   투명성의 차이를 재려면 더 큰 단위(파일 여러 개, 상호작용)나 더 어려운 질문, 또는 사람 독자가 필요합니다.
6. **비용이 가장 많이 든 곳은 오라클이었습니다.** 테스트 서버, 숨겨진 테스트, 벤치마크, 프로브를 만들고 네 번 고치는 데 실험군 하나를 돌리는 것보다 훨씬 많은 시간이 들었습니다.

## 회의론자 라운드: W3 → W4 ([arms/w4/ROUND.md](arms/w4/ROUND.md))

W3에 대한 지적 16건 중 재현 가능한 것을 먼저 테스트로 만들었습니다. 그중 구현과 무관한 3건은 숨겨진 테스트로 넣었는데(23 → 26개), **3건 모두 원본에서도 재현됐습니다**. 단일 스트림이 일부만 담은 206을 완성본으로 받는 결함, 프로브와 구간 응답의 총량이 다를 때 잘린 파일을 내놓는 결함, 빈 본문에서 취소를 놓치는 결함입니다. 그다음 고쳤고, 고친 자리를 되돌려 테스트가 실패하는지 확인했습니다.

## 소유자 결정과 W5 → W7 ([INTENT.md](INTENT.md) Revision 1)

소유자가 추천안을 승인했습니다.

- **옛 형식 재개 파일**: 마이그레이션 코드를 넣지 않습니다. 당시 `F:\VNovel`에 `.download*` 파일이 0개였고, 버전을 바꾸기 전에 멈춘 다운로드를 정리하면 됩니다.
- **넣은 것**: 멈춘 서버 감지(30초 무응답이면 실패로 보고 재시도), 탐색 요청 재시도, 서버가 침묵하는 중에도 1초 안에 취소.
- **넣지 않은 것**: 단일 스트림 자동 재시도(0부터 다시 받게 됨), fsync.

INTENT를 먼저 고쳤고, 테스트 서버에 "연결을 연 채 침묵"과 "첫 탐색 끊기" 모드를 넣어 숨겨진 테스트 3개를 추가했습니다(26 → 29개). 그다음 회의론자 라운드를 두 번 더 돌았습니다.

| 버전 | 한 일 | 코드 줄 | 자체 테스트 | 숨겨진 테스트 29개 | 회의론자: 새 회귀 |
|---|---|---|---|---|---|
| W5 | `wait()` 하나로 응답·청크 대기를 모아 1초마다 취소 확인 + 30초 정체 감지. 탐색 요청 재시도 | 429 | 21 | 29 | 2 (높음 1: 길이 헤더 없는 초과 응답) |
| W6 | 3차 지적 수정: 넘겨받기로 줄지 않은 구간은 응답 끝까지 확인, 단일 스트림의 크기 모순 감지, 재시도 대기 중 취소, 단일 스트림도 옛 상태를 먼저 지움 | 448 | 24 | 29 | 1 (중간: 끝나지 않은 응답이 성공으로 처리됨) |
| **W7 (병합)** | 4차 지적 수정: 채운 뒤 확인 읽기가 실패하면 오류, 단일 스트림은 알려진 크기를 넘는 순간 중단 | **452** | **26** | **29** | 멈춤 |

**중단 기준**: 라운드마다 새 회귀는 7 → 2 → 2 → 1로 줄었고, 심각도도 높음에서 중간으로 내려갔습니다. 마지막 한 건도 재현 테스트로 막았습니다. 고칠 때마다 그 자리를 되돌리면 테스트가 실패하는지 확인했습니다(돌연변이 검사). 타이밍에 기대는 테스트는 5회 반복해서 흔들림이 없음을 확인했습니다.

**병합 전 최종 확인 (W7)**: 앱 전체 `cargo test` 421개 통과, 모듈 clippy 경고 0. 벤치마크는 원본과 번갈아 쟀습니다(80MB 연결당 제한 1.08s, 느린 연결 섞임 2.31s, 512MB는 원본과 같은 범위). 공개 HTTPS 서버와 GitHub 리다이렉트에서 원본과 바이트 단위로 같은 파일을 받았습니다.

**병합**: `main`을 `exp/northstar-segmented`로 fast-forward했습니다(`c97cbff..c4800eb`, 커밋 5개, 푸시하지 않음). 진단 로그 커밋도 포함했고, ARCHITECTURE의 다운로드 서술도 함께 고쳤습니다. 원본 556줄은 452줄이 되었습니다(−19%). 크기는 W3의 371줄이 가장 작았고, 그 뒤 회의론자 라운드에서 81줄이 늘었습니다. 늘어난 줄은 모두 D5~D7(서버 오동작, 정체, 취소)을 지키는 데 쓰였습니다.

남은 것으로 기록만 한 항목: 잠금 안 동기 파일 쓰기, fsync, 다른 호스트로 리다이렉트될 때 쿠키를 잃음(reqwest의 보안 동작), 같은 크기의 다른 파일이면 섞임, 정리 실패 무시. 모두 머리말 `Weak:`와 [INTENT.md](INTENT.md)에 적어 두었습니다.

## 한계

- 모듈 하나, 각 실험군 1회 실행입니다. 반복하지 않았으므로 운의 몫을 분리하지 못했습니다.
